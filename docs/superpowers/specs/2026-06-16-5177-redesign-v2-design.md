# 5177 本地控制台重设计 v2

## 背景

当前运行在 5177 端口的本地网页此前经历过多轮设计探索，但用户已明确推翻之前的 Tabler、类 Tabler、深色、Qt 风格与混合定制化实现，要求收敛到一个更直接、更克制、完全标准化的方向。

本次设计以 **原生 Bootstrap 风格** 为唯一视觉约束，目标不是构建一个自定义设计系统，而是把当前桥接控制台信息重新组织为一套清晰、稳定、低装饰、易实现的 Bootstrap 页面。

## 用户已确认的硬约束

1. 必须使用中文界面文案。
2. 页面结构顺序固定为：顶部导航栏 → 状态区 → 微信通道 → 配置 → 会话。
3. “微信通道”需要上移，放在更靠前的位置。
4. “配置”需要放在顶部区域，而不是靠后。
5. “当前会话”和“接入会话”必须放在同一个组件中，但视觉上仍然区分为两个子块。
6. 不要深色主题。
7. 不要 Qt 风格。
8. 不要 Tabler 风格。
9. 必须是 **完全原生 Bootstrap 风格和样式**。
10. **不要添加任何非 Bootstrap 效果和事件**。
11. 不要额外的自定义 hover、动画、transition、特效、高亮体系或自定义交互逻辑。

## 设计目标

### 1. 降低设计感，提升标准化

页面应看起来像一个标准的 Bootstrap 管理页，而不是一个额外定制过的品牌化产品页。视觉重点来自信息组织与 Bootstrap 自带组件层级，而不是来自个性化装饰。

### 2. 保持操作台属性

页面仍然是本地桥接控制台，因此需要保留：状态概览、微信连接信息、配置编辑、当前会话状态、可接入会话列表。这些信息密度不能因重设计而下降。

### 3. 降低实现复杂度

新设计必须允许前端实现时主要依赖 Bootstrap 原生组件与 utility class 完成，尽量避免额外样式抽象、视觉 token、动画逻辑与复杂交互状态管理。

## 视觉原则

### 总体风格

- 使用 Bootstrap 默认浅色语义：`bg-body-tertiary`、`bg-light`、`text-muted`、`btn-primary`、`btn-outline-*`、`alert-*`、`badge`、`card`、`table`。
- 背景保持浅灰或白色体系。
- 组件边界依赖 Bootstrap 默认边框、圆角、留白。
- 所有视觉反馈以 Bootstrap 默认状态为上限，不新增任何额外 hover 或 motion。

### 字体与文本

- 正文使用系统默认 sans-serif，跟随 Bootstrap 默认字体栈。
- 路径、会话 ID、端口、PID、平台 ID 等技术字符串使用 `font-monospace`。
- 页面副标题与字段标签允许使用 Bootstrap utility（如 `text-uppercase`、`small`、`fw-semibold`、`text-muted`）表达较弱层级，但不引入额外的自定义文字系统。

### 图标

- 允许使用 `bootstrap-icons`。
- 图标只用于辅助识别，如刷新、桥接、断开连接等。
- 图标不承担额外交互动画效果。

## 页面信息架构

### 1. 顶部导航栏

使用 Bootstrap 原生 `navbar`。

内容：
- 左侧：应用名 `claude-codex-wechat`
- 中部或主导航区：`控制台`、`日志`、`设置`
- 右侧：一个简短在线状态徽章 + 刷新按钮

要求：
- 结构上是标准 navbar，不做自定义顶栏变体。
- 刷新按钮仅作为页面动作入口表现，不在设计层定义额外交互。

### 2. 页面标题区

位于 navbar 下方。

内容：
- 主标题：`桥接控制台`
- 副标题：简短的状态性文字，例如 `概览 · 实时`

要求：
- 使用 Bootstrap 常规标题层级，如 `h3` + `small/text-muted`。
- 不做 hero 区，不做 banner，不做图形背景。

### 3. 状态区

使用 Bootstrap 栅格与 card 组织成 4 个状态卡片：
- 桥接
- 微信
- claude
- codex

每个卡片包含：
- 状态名
- 状态值（如运行中、已连接、已检测、未找到）
- 一行较弱的补充信息（端口、用户名、版本、错误码等）

要求：
- 使用原生 `card`。
- 使用 Bootstrap `badge` 表达小状态点或颜色状态。
- 不使用自定义统计卡片组件。
- 不增加 hover 强化或卡片抬升效果。

### 4. 微信通道

使用一个独立 `card`。

内容包括：
- 机器人
- 用户
- 平台 ID
- 网关
- 断开连接按钮

建议结构：
- `card-header`：标题 + 右侧弱说明
- `card-body`：使用 `dl.row` 或 `row + col` 的标准信息布局
- 底部右侧：`btn btn-outline-danger`

要求：
- 信息表达清晰即可，不做自定义 key-value 组件。
- 技术值使用 `font-monospace`。

### 5. 配置

使用一个独立 `card`。

内容包括：
- 提供方选择
- 工作目录输入
- 保存按钮
- 一行弱提示文本

要求：
- 采用标准 Bootstrap form：`form-label`、`form-select`、`form-control`、`btn btn-primary`
- 不做 inline 编辑特效
- 不做即时保存反馈设计扩展

### 6. 会话

使用一个 card，内部明确分成两个子块，但仍属于同一个组件。

#### 6.1 当前会话

位于 card 内上半部分。

内容：
- provider 徽章
- 目录
- 进程
- 启动时间
- 停止会话按钮

推荐使用：
- Bootstrap `alert alert-primary` 作为当前会话容器
- 内部用 inline 文本块或小型 row 展示字段

原因：
- `alert` 是 Bootstrap 原生组件，能自然把当前会话与下方可接入列表区分开，而不需要自定义高亮块。

#### 6.2 可接入会话

位于当前会话下方。

内容：
- provider tabs（如 `claude-code` / `codex`）
- 会话列表表格
- 每一行的接入按钮

推荐使用：
- `nav nav-tabs`
- `table` 或 `table table-hover`

字段：
- 会话
- 目录
- 更新
- 操作

要求：
- 与当前会话处于同一张 card 内
- 但通过标题、小分段文字、alert 与 table 的天然组件差异实现视觉区分
- 不做自定义分栏容器或特殊边框体系

## 组件映射

本设计应优先映射为以下 Bootstrap 原生组件：

- 顶栏：`navbar`
- 页面布局：`container-fluid`、`row`、`col-*`
- 内容块：`card`
- 当前会话：`alert`
- 状态标识：`badge`
- 表单：`form-control`、`form-select`、`form-label`
- 操作按钮：`btn`、`btn-primary`、`btn-outline-secondary`、`btn-outline-danger`、`btn-outline-primary`
- 会话切换：`nav nav-tabs`
- 会话列表：`table`
- 技术文本：`font-monospace`

禁止为了“更好看”而引入的内容：
- 自定义 token 系统
- 自定义卡片状态条
- 自定义 hover 或 active 动画
- 自定义阴影层次
- 自定义交互事件
- 非 Bootstrap 的局部视觉语言

## 数据与行为边界

本次只重定义前端页面结构与呈现方式，不改变现有数据协议与业务语义。

### 保持不变

- `src/web/apiClient.ts` 的接口契约
- 当前页面已有的数据来源
- 微信连接、配置保存、会话停止、会话接入等动作的业务语义

### 可以改变

- 组件层级
- DOM 组织方式
- 标题和字段的呈现布局
- 为满足纯 Bootstrap 设计而进行的文案微调

### 不在本次范围内

- 新功能增加
- 新业务状态增加
- 新的前端动效系统
- 自定义设计系统建设
- 后端 API 变更

## 测试影响

由于页面结构会明显重组，前端测试预计需要更新。

重点影响点：
1. 标题、按钮、tab、字段标签的文本查询位置变化。
2. 组件层级从现有自定义布局切换为 Bootstrap 风格结构后，部分 DOM 结构断言会失效。
3. 当前会话与可接入会话被放入同一个 card 内后，测试需要按新的分段结构定位。
4. 如果当前测试依赖旧的文案顺序或旧的 section 包装结构，需要同步调整。

测试更新原则：
- 保留原有功能语义断言
- 减少对自定义样式结构的依赖
- 尽量按用户可见文本和标准可交互元素查询

## 实施策略

### 阶段 1：页面骨架重组

- 重写 `App.tsx` 顶层布局
- 确认页面顺序为：navbar / 标题 / 状态 / 微信通道 / 配置 / 会话

### 阶段 2：WeChatPanel 结构重组

- 将微信通道、配置、会话收敛为新的 Bootstrap 页面区块
- 把“当前会话”和“可接入会话”整合到同一 card 中

### 阶段 3：样式收缩

- 删除或替换现有非 Bootstrap 风格样式
- 尽量将 `src/web/styles.ts` 收缩到最小，或仅保留必要兼容层
- 不再维持 Tabler 风格 token

### 阶段 4：测试更新

- 更新受影响的 web 测试
- 确认核心交互仍然能通过已有流程工作

## 风险与取舍

### 风险 1：页面变得“太普通”

这是用户明确要求接受的取舍。目标不是追求品牌感，而是回到稳定、原生、低定制的 Bootstrap 控制台。

### 风险 2：纯 Bootstrap 不足以表达“当前会话高亮”

设计上通过 `alert alert-primary` 解决，而不是引入自定义当前态容器。

### 风险 3：测试对旧结构耦合较高

需要同步修改测试，但这是可接受成本，因为设计方向已被彻底重置。

## 最终设计结论

最终页面应呈现为一个 **完全原生 Bootstrap 风格的本地控制台**：

- 顶部是标准 navbar
- 主内容是标准 container + row + card
- 微信通道与配置上移
- 会话被合并到同一张 card 中
- 当前会话通过原生 alert 区分
- 可接入会话通过原生 nav-tabs + table 呈现
- 不添加任何非 Bootstrap 效果、样式体系或事件逻辑

这份设计是后续实施计划的唯一依据。
