# 多会话接入与管理 优化设计

> 状态:设计稿(未开始实现)
> 日期:2026-06-30
> 目标读者:本项目维护者
> 范围:理清「要做什么 / 为什么」,不含具体代码实现

---

## 0. 一句话目标

让**一个微信用户**能在**同一个引擎**(Claude 或 Codex)下**同时接入并保留多个会话**,并对它们进行**管理**(列出、切换、接入、移除)。

---

## 1. 背景与诉求

- 用户经常在**多个工作目录(`cwd`)**下分别有 Claude / Codex 会话;
- 希望在微信侧能**同时挂着这些会话**、按需在它们之间**切换**,而不是一次只能用一个;
- 目前的限制:一个微信用户在一个引擎下**只能保留一个会话**——接入新的会话会把旧的**顶掉**。

---

## 2. 现状分析

### 2.1 已干净确认的事实 ✅

**(a) 会话标识结构**(`src/session/currentConversationStore.ts`,`CurrentConversationSchema`):

| 字段 | 含义 | 约束 |
|------|------|------|
| `bridgeSessionId` | 桥接会话唯一 id | 必填 |
| `providerSessionId` | 底层原生 Claude/Codex 会话 id | 可选 |
| `providerId` | 引擎(claude-code / codex) | 必填 |
| `chatId` | 微信会话 / 对话 id | 必填 |
| `ownerUserId` | 归属的微信用户 id | **可选** |
| `cwd` / `title` / `updatedAt` | 上下文与描述 | 可选 |

**(b) 存储是「全局单值」**:`getCurrent()` 从 KV 存储读取**单个** key(`CURRENT_CONVERSATION_KEY`),只返回**唯一一个** `CurrentConversation`。
→ 这正是「同一引擎下只能保留一个会话」的直接原因:系统在存储层面只认识「一个当前会话」。

**(c) 绑定入口**:`SessionManager.ensureBridgeSession({ providerId, chatId, platformUserId, cwd?, providerSessionId? })`(`src/session/sessionManager.ts`)。

**(d) 进程 / 会话恢复层已支持长驻多会话**:
- Claude 默认走长驻 streaming runner,按会话各自持有常驻子进程(可并存多个);
- Codex 默认走长驻 app-server,单进程内用 sessionId 区分多个会话;
- **runner 层没有「同一时刻只允许一个会话」的限制。**

### 2.2 核心结论

> **多会话能力的瓶颈不在进程 / 恢复层(那层已经 ready),而在「会话标识的存储模型」——它把多维标识坍缩成了一个全局单值。**

`CurrentConversationSchema` 里本就有 `chatId`、`ownerUserId`、`bridgeSessionId` 这些「区分不同会话 / 不同归属」的维度,但存储只用一个全局 KV key、没有按这些维度组织成集合。把存储从「单值」升级为「池」,即可解锁多会话。

## 3. 目标设计:会话池模型

### 3.1 模型概览

```
会话池(Session Pool)
  └─ ownerUserId(微信用户)
       └─ providerId(引擎)
            ├─ 会话A { bridgeSessionId, providerSessionId, cwd, title, ... }
            ├─ 会话B { ... }
            └─ 会话C { ... }
  + 焦点指针:每个 (ownerUserId, providerId) 记录「当前焦点会话 = bridgeSessionId」
```

一句话:**会话池容纳多会话(每个带唯一标识 + 归属);每个用户在每个引擎下有一个焦点指针;消息默认发给焦点会话,切换焦点才用标识。**

### 3.2 会话标识 —— 已现成

- 每个会话的唯一 key 直接用 **`bridgeSessionId`**;
- 归属维度用 **`ownerUserId`**(建议从「可选」改为「必填」),`chatId` 作为对话通道键,两者语义分开(一个是「人」,一个是「对话渠道」);
- 可为会话再配一个**人类可读 handle 别名**(便于将来用 `@handle` 选择,非首期必需)。

### 3.3 焦点指针 —— 必须有

微信是**线性对话流**,用户不可能每条消息都先报一个 session id。因此池之外要有「当前焦点会话」:
- 默认:消息发给焦点会话;
- 切换:才需要用标识 / handle / 网页点选指定换到哪个。

### 3.4 消息路由:按「用户 + 焦点」选定会话

入站消息处理两步:
1. 按发信人的 `ownerUserId` / `chatId`,**取出「属于该用户」在该引擎下的会话子集**;
2. 在子集里投给**焦点会话**(取代当前无条件取全局当前会话的方式)。

## 4. 会话管理能力(本次的产品面)

围绕「一个微信用户在一个引擎下管理多个会话」,需要提供:

| 能力 | 网页 | 微信命令 |
|------|------|----------|
| **列出**该用户某引擎下的所有会话(按 `cwd` 分组) | ✅ | 可选 `/sessions` |
| **标记**当前焦点会话 | ✅ | — |
| **接入**新会话(**不再顶掉**旧的,而是加入池) | ✅ | — |
| **切换**焦点会话 | ✅ 点选 | `@handle` / `/switch` |
| **移除 / 解绑**某个会话 | ✅ | 可选 |

> 网页是主要管理入口;微信侧至少要能「切换焦点」,其余可后续补。

## 5. 分阶段实施(由地基到上层)

> 每阶段独立可用、可验证。先打地基,再逐层加功能。

### 阶段 1 — 地基:单值 → 会话池 + 焦点指针
- 把 `CurrentConversationStore` 从「全局单值」升级为「按 `(ownerUserId, providerId)` 的会话集合 + 焦点指针」;
- 入站路由改为「按归属取子集 → 投焦点会话」;
- 此阶段即使每个引擎仍只放一个会话也能跑通,是后续一切的地基。

### 阶段 2 — 同引擎多会话接入 + 网页管理
- `ensureBridgeSession` 调整为「按会话标识增量加入池」,接入新会话不再覆盖旧的(落点见 §2.3 复核项);
- 网页:按 `cwd` 列出该用户在该引擎下的会话,标记「当前焦点」,支持接入 / 移除。

### 阶段 3 — 焦点切换
- 引入 handle 别名;
- 网页点选切焦点 + 微信侧 `@handle` / `/switch` 切焦点;
- 默认焦点策略见 §7 开放决策。

### 阶段 4 — group(后续可扩展,非首期)
- 新增 group 容器:把若干已接入会话打包成组,便于整组切换 / 激活;
- 组内仍由焦点 / `@` 决定当前对话对象。

> 说明:**进程 / 会话恢复机制无需改动**,以上全部建立在现有长驻多会话能力之上(§2.1d)。
